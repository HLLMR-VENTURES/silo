# Shareable collections — design (post-v0.2.0)

**Status: Phase 1 shipped** (share / preview / import a mod set via a secret gist — epic #61,
PRs #63–#69). The rest of this document is the original design, kept for the later phases.

Goal: let a user share a mod set — a loadout / active set, optionally bound to a savegame —
as a **GitHub artifact under their own account**, and let anyone import it into Silo in a
click. Private link-shares for multiplayer groups; public, discoverable "mod groups" for the
community. Leverages the GitHub auth most users already granted (star/watch), holds no user
data, and never rehosts a mod ZIP.

## Why it's mostly assembly, not new invention

Every hard piece already exists:

- **The manifest** — `mpsync` already exports a *hashed manifest of the active set* and diffs
  a joiner's library against it (missing / wrong-version / different-file / extra). That is the
  MP import loop, already written.
- **Loadouts** already serialize to a `.silo` file and re-import. A share is that payload over a
  different transport.
- **Resolve + install** — the catalog resolves `techName → sources → download URL`;
  `install_remote_mod` pulls it; loadout-create wires it into a profile.
- **GitHub auth** — device-flow token, `public_repo` scope, already held for most users.
- **Provenance** — a collection carries each mod's canonical `manifestHash`, so an import can
  **verify it installed exactly what the author ran**. No counterfeit collections.

New code is small: create/push a gist-or-repo, an import-from-URL command, and a resolve-preview
UI (the organize-preview pattern, reused).

## The manifest

A collection is metadata + a mod list + optional savegame binding. Extends the existing
`.silo`/`mpsync` shape:

```jsonc
// silo-collection.json  (also the public-repo discovery marker — see Phase 3)
{
  "schema": "silo.collection/1",
  "name": "Seasons Co-op — Autumn 2026",
  "description": "The set our group runs. GitHub mods import automatically.",
  "author": "hllmr",                 // the GitHub login that created it
  "createdAt": "2026-08-01T...Z",    // stamped client-side at export
  "savegame": { "name": "savegame3", "mapTitle": "..." },   // optional binding
  "mods": [
    {
      "techName": "FS25_CabView",
      "version": "v1.0.2.9",
      "source": "github",            // preferred source for this mod
      "sourceUrl": "https://github.com/.../releases/tag/v1.0.2.9",
      "manifestHash": "9fea10cd…",   // canonical hash (provenance), when known
      "installable": true            // false → importer opens the page (ModHub)
    }
    // …
  ]
}
```

Lists and pointers only — **never the mod ZIPs** (same no-rehost rule as SiloAPI; keeps it
legally clean and consistent with the whole architecture).

## Transport — the scope decision that shapes everything

Creating a **public** repo needs `public_repo` (**already held**). Creating a **private** repo
needs the full `repo` scope — read/write to *all* the user's private repos, a scary ask.
So we do **not** use private repos. Instead:

| Share type | Transport | Scope | Notes |
|---|---|---|---|
| **Private / MP** | **Secret gist** | `gist` (one added scope → a one-time re-connect) | Unlisted, shareable by link only. "Private" = link-only, **not** auth-gated. |
| **Public / mod group** | **Repo** | `public_repo` (have it) | Silo generates a README (mod list, source links, provenance badges, "Open in Silo"). Star-able, forkable, versioned, discoverable. |

True auth-gated private (org/team) would need `repo` scope + a private repo — punt to a later
phase; secret-gist link-sharing covers the MP use case without it.

## Flows

**Export** (explicit, consented, clearly Silo-authored):
1. User picks a loadout / the active set (+ optional savegame binding), Private or Public.
2. Build `silo-collection.json` from the current set + catalog data + provenance hashes.
3. Private → `POST /gists` (secret). Public → `POST /user/repos` then put `silo-collection.json`
   + a generated `README.md`. The README says **"Generated by Silo"** and links to the app.
4. Return the URL to share.

**Import**:
1. Paste a gist/repo URL (or, Phase 3, pick from Browse Collections).
2. Fetch the manifest, resolve each mod against the catalog.
3. **Preview** (organize-preview pattern): what will install (GitHub-source), what needs a manual
   "open the page" step (ModHub), what's already present, and — via provenance — which
   resolved mods verify against the collection's declared hashes.
4. Install the installable set, then create/apply a loadout (bound to the savegame if present).
5. **MP path:** `mpsync` diffs the host's manifest against the joiner's library and shows the
   fix-list. "Host shares a link, joiner clicks import, Silo fixes the diffs."

## Provenance synergy

Because the manifest carries canonical `manifestHash`es, an import verifies each installed mod
against the author's build. "Verified, shareable, importable modpacks" is something no
competitor can follow — it rides the same cross-source hash DB that is the moat.

## Phasing

- **P1 — MP share via secret gist.** Highest value, lowest scope; reuses `mpsync` + catalog +
  install almost entirely. Adds the `gist` scope, gist create/read, import-from-URL + preview.
- **P2 — public collections as repos** with the generated README + an "Open in Silo" deep link
  (URL paste or a `silo://` handler).
- **P3 — discovery (infra chunk).** SiloAPI indexes public repos containing `silo-collection.json`
  → a **Browse Collections** tab, provenance-verified, star-ranked. See the contract below.

## SiloAPI indexing contract (Phase 3)

- Discover public GitHub repos with a root `silo-collection.json` (GitHub code search on the
  marker filename/schema key), same polite-citizen rules as the rest of ingest.
- Validate the manifest schema; resolve its mods against the canonical DB; store a `collection`
  record (name, author-login, mod count, resolvable %, star count, provenance-verified %).
- Serve a read API (`GET /collections`, `GET /collections/:id`) for the client's Browse tab.
- **No user data, no writes** — collections are public GitHub repos; SiloAPI only indexes them,
  same posture as mod sources. Honor takedowns/`deleted` repos on re-crawl.

## Caveats to message honestly

- **"Private" = unlisted link, not auth-gated** (v1). Say so.
- **ModHub mods = guided import**, not one-click (their CDNs gate downloads). GitHub-source
  collections are the frictionless ones — worth nudging authors toward GitHub releases.
- **Version drift:** a collection pins versions; a ModHub latest-only source may no longer
  serve the pinned build → provenance correctly reports "the pinned version is gone" (not a bug).
  GitHub release assets persist, so GitHub-source collections age best.
- **Writing to a user's GitHub account is trust-sensitive:** creation must be explicit, consented,
  revocable, and the artifact clearly Silo-authored.
- **Save-file sharing is out of scope for v1** — savegames are large (gist/repo size limits) and
  useless without the same mod set anyway. The mod-set is the enabler; ship that first. Revisit
  save sharing later over a repo with LFS if it earns its keep.

## Relationship to the A/B/C platform strategy

This is a **lightweight bridge toward Option C** (`SiloAPI/docs/DESIGN.md` — authors publishing
first-party). User collections hosted on GitHub give Silo a distribution/social layer **without**
Silo hosting any files or taking on the legal/mirror burden — it rides GitHub. Public collections
also generate demand signal ("players want to ship curated sets through Silo") that de-risks the
eventual first-party publishing platform. Keep the two distinct: collections share *lists*;
Option C hosts *files*.
